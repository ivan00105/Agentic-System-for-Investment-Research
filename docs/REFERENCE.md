## 1. System rules (non-negotiable)

| Rule | Why |
|---|---|
| The LLM never does arithmetic or invents numbers. Every number comes from a tool result and is cited by ID. | LLMs make arithmetic and unit mistakes. |
| The data layer enforces the cutoff date, whatever the prompt says. | Prevents look-ahead. |
| The model's memory is not evidence: a report uses nothing from after the cutoff, even what the model remembers (`rules.md` rule 8, critic issue `look_ahead`). | The model was trained after most eval cutoffs, and the data layer can't stop what it already knows. |
| Missing or incompatible data means **unknown**. It is never zero, and it never passes a screen. | Silent zeros produce fake results. |
| Keep reporting period, availability (filing) date and retrieval date separate. | A Q1 filing is not available in Q1. |
| Retrieved text is **data**. It can never change policy, the cutoff or the tool list. | Prompt injection. |
| Hitting a limit never upgrades a claim to "supported". | Honest partial results. |
| Run status, report support, screen eligibility and outlook status are separate fields. | One "confidence" number hides failures. |
| Outlook numbers (forecast probabilities and ranges, base rates, implied growth, factor exposures) are host-made records. LLM narrative cites them and never edits them. | Keeps the outlook evaluable. |
| No synthetic data is ever substituted for a failed live fetch. | Honesty. |

## 2. Analyst role contracts

All roles are **the same agent loop** with a different prompt and tool subset. Only the coordinator writes the authoritative state. Specialist outputs are proposals.

| Role | Does | Tools | Must not |
|---|---|---|---|
| **Coordinator** | Plans; dispatches analysts; picks the next action, citing the unresolved item it addresses; synthesizes; decides each objection's outcome; sets the final status | all analysts as sub-calls (`ask_<analyst>` tools in its loop), `find_company`, `calculate`, `screen`, `get_peers` | Bypass evidence rules or write numbers itself |
| **Fundamentals analyst** | Finds the right periods and concepts; computes margins, growth, FCF; flags comparability problems (fiscal year, units, restatements) | `find_company`, `get_financials`, `calculate`, `verify_against_filing` | Do arithmetic in prose |
| **Filings & events analyst** | Reads 10-K sections (risks, MD&A), 8-K events and insiders' Form 4 trades; separates event date from publication date; attributes management claims | `find_company`, `read_filing_section`, `list_filings`, `get_insider_trades` | Treat management claims as established fact |
| **Market & valuation analyst** | Price history, returns, volatility, drawdown, Sharpe ratio, valuation ratios, returns against peers and the sector ETF; rates and macro release dates as context | `find_company`, `get_prices`, `get_financials`, `calculate`, `get_macro`, `get_peers` | Present adjusted historical prices as tradable prices |
| **Outlook** (not an LLM, §6) | Risk, business and direction forecasts, implied growth and factor exposures, each a record with its track record | `get_outlook`, `get_base_rates`, `get_factor_exposures`, `calculate` (`implied_growth`) | Be changed by narrative |
| **Critic** | Returns zero or more objections, each tied to a claim version, with an issue type and a requested check | read-only tools + `verify_against_filing` | Be bearish by default, edit evidence, or close an objection by agreeing |

The action trace saves short rationales, not chain-of-thought. A repeated action with no new inputs is skipped (action fingerprint).

Tool lists are enforced (`agents/roles.py`): the loop answers a call to any other tool with an "invalid" result. Decided in Phase 3: every tool the single agent (condition B) has belongs to some role in C, so B vs C isolates specialization rather than tool access. So every analyst can `find_company`, the market analyst also reads `get_financials` (market cap needs a share count, P/E needs earnings), fundamentals has `verify_against_filing` (the critic gets it too in Phase 4), and the coordinator can `calculate` across analysts' records. An analyst keeps its conversation, so the coordinator's follow-up builds on its earlier work; a follow-up lists the analyst's earlier findings by claim ID, so it can revise one as a new version. Decided in Phase 4: the critic's read-only tools are `find_company`, `get_financials`, `calculate`, `read_filing_section`, `list_filings` and `get_prices`, plus `verify_against_filing`; `screen` is left out, since reviewing one report never ranks companies. The November data tools (`get_macro`, `get_insider_trades`, `get_peers`) went to the analyst whose question they answer and to the critic, which only reads; the coordinator also has `get_peers`, so it can hand every analyst the same peers.

## 3. Claims, objections and outcomes

- **Claim:** ID, **version**, statement, type (fact / calculation / interpretation), materiality (central / supporting / minor), cited fact, calculation or chunk IDs, status.
- **Objection issue types:** unsupported inference, contradictory evidence, wrong period/unit/entity, arithmetic error, stale source, misleading certainty, missing material risk, look-ahead (added 11 Nov 2026: something from after the cutoff that no cited record shows).
- **Outcomes** (one taxonomy, used everywhere):
  - **defended**: evidence answers the objection, and the check is cited.
  - **corrected**: a new claim version is created, and dependent calculations and claims are recomputed.
  - **withdrawn**: the claim is removed, and dependent conclusions are reconsidered.
  - **unresolved**: the issue and its impact are shown.
- Each outcome must cite evidence or a calculation. A resolution on claim v1 does not validate v2. Track objections by ID, not by count.
- Each report section carries a status: **cited / qualified / abstained**. Qualify a single section rather than abstaining from the whole report. *Cited* only means every statement cites real tool records and the checker flagged nothing; whether the evidence really supports the statement is judged in evaluation (§7).
- Stop reviewing when no material objection has a feasible next action. More debate rounds can make results worse (Kaesberg et al. 2025).
- **How Phase 4 applies this** (`agents/critic.py`): "wrong period/unit/entity" is three issue types, so the evaluation can score each. An objection ID comes from its claim, version, issue and wording; the same issue on the same claim version again is a repeat and isn't routed (no new input, so no feasible next action). The **claim ledger decides** whether a claim changed, not the coordinator's word: a claim gone from the report is withdrawn (recorded in `ClaimLedger.withdrawn`), a new version is corrected only when the coordinator calls it corrected and cites evidence, and an unchanged claim can only be defended (with at least one cited record) or unresolved. One exception: a missing material risk is corrected by the claims the revision adds, when they and the outcome cite evidence, since the claim it qualifies may rightly stay as it was. An answer that doesn't fit (defended with no citation, "corrected" with the claim unchanged, a changed claim without a cited "corrected", no answer) leaves the objection open with a note, and it goes back to the coordinator next round. The guard is `AGENT_CRITIC_ROUNDS` reviews (3), so at most 2 revisions; what the last review raises, and anything still open, ends unresolved with the reason. A material objection left unresolved, or a citation of a withdrawn claim, flags the claim, so its section is **qualified**; an unresolved objection follows its claim ID to every later version, since only evidence closes it; a claim that cites a claim with such an objection is flagged too (one step only, no full dependency graph). The coordinator is told who owns each claim (the analyst that wrote it, else one whose finding it cites, else itself); answering without asking that analyst is noted, not blocked.

## 4. Discover mode rules

1. Turn the question into a **ScreenSpec**: universe, filters (sector, revenue growth, margin, FCF > 0, valuation…), top-k, ranking rule. **Show it to the user.**
2. A vague term ("cheap", "safe", "best") gets a clarification question or an explicitly stated definition. Never silently invent one.
3. Each filter returns pass / fail / unknown. Unknown never passes. Ties break on a stable ID, never alphabetically by design.
4. Research the ranked candidates. If research finds a filter violation, exclude the candidate with its provenance and pull in the next one.
5. Show counts: screened, eligible, investigated, rejected, returned. Returning fewer than k is fine.
6. Every final pick must pass a deterministic acceptance test on validated facts.
7. Never imply the search covered "the whole market" unless the universe really was the whole market.
8. For a cheap first pass over many companies, the SEC **frames** API returns one concept for all filers in one call. Caveat: frames are calendar-aligned and return each company's **latest-filed** value (restated, not point-in-time), so verify shortlisted names with companyfacts. A company's value comes from the best tag it reports, but a larger total (`Revenues`, `SalesRevenueNet`, `RevenuesNetOfInterestExpense`) for the same period and filing (accession) replaces ASC 606 contract revenue (a larger total from another filing is kept out and noted on the row, so an older figure never overrides a later corrected one), which leaves out lease income and interest: UDR, a REIT, reported $11M of contract revenue against $1.7B in total, so its operating margin showed as 4,870%. A margin above 100% (`SCREEN_MAX_MARGIN`) or inputs whose fiscal years end more than a week apart (`SCREEN_PERIOD_SLACK_DAYS`) is flagged unknown with its reason. The value stays in the screen record, but it never passes a filter and is never ranked. BitMine's operating income, mostly crypto gains, was 73 times its revenue. On the CY2025 frames for every filer, this cut the operating margins above 100% from 31 to 11, and all 11 are flagged.
9. **Discover runs on current data only.** Frames aren't point-in-time, so a Discover with a past cutoff would already have used later information, and checking the shortlist afterwards can't undo that. For the same reason the `screen` tool answers "invalid" in any run with a past cutoff (a Check or Compare with `--cutoff`, the web page's cutoff, every evaluation case). Screen on fundamentals first, then check valuation (which needs prices) on the shortlist. Say for each metric which filers it covers (banks, IFRS filers, ADRs). Never describe the result as "the cheapest in the market".

**How Phase 5 applies this** (`agents/discover.py`, CLI `--universe`): a declared universe is a YAML file (name, source, date, companies with ticker and CIK); the bundled `sp500_tech` is today's S&P 500 Information Technology and Communication Services members from Wikipedia's constituents table (97 tickers, 94 companies), so it is survivorship-biased. A screener role (`prompts/screener.md`, no tools) writes the spec: `screen` filters, ranking, top-k, **price checks** (P/E, P/S, P/B, FCF yield, market cap, volatility, drawdown; these need prices, so they run per candidate, never in the screen) and every vague term with its definition and a question. An interactive terminal asks each question (Enter accepts the proposal), `--define TERM=MEANING` answers up front, and an unasked term is shown as "assumed: not confirmed by the user"; an answer goes back to the model, which revises the spec. `screen` ranks the whole universe; then the host walks the ranking: the **acceptance test** (`agents/acceptance.py`, rule 6) recomputes every filter on the latest 10-K (companyfacts, via `get_financials` and `calculate`) and every price check on the latest close, with no model, and each line cites its record; unknown fails. A candidate that passes gets a research run by condition B, C or D, with its own trace. A rejected candidate or a failed research run (one that failed, or ended with no claims in any section) is replaced by the next one; research runs are limited to top-k plus `DISCOVER_MAX_REPLACEMENTS` (3, `--replacements`), rejections cost no model call and don't count. Counts: screened, passed the screen, ranked, checked, rejected, researched, research failed, replaced, returned. The Discover trace holds the spec step, the host's tool calls (so the checks are frozen evidence) and one event per candidate; its `run_end.totals` add the research runs'. `--cutoff` is refused with `--universe` (rule 9). **The code check decides eligibility**, with the spec's definitions; a pick's research may use another one (a trailing P/E, say) and doesn't decide again, so the shortlist shows the acceptance lines next to each pick and a difference stays visible. A line built on USD figures that are probably convenience translations (another currency is reported too) says so and names its basis: "USD as filed"; a line built on converted figures names the currency and the rate source ("converted to USD"). Insider checks (`insider_purchases`, `insider_sales`, `insider_net_purchases`, `insider_buyers`, from `get_insider_trades` over the last year) run per candidate like price checks; a foreign filer files no Form 4, so it comes back unknown, and so does one whose Form 4s couldn't all be read (status partial).

**From the web page** (Phase 7), "Find companies" starts the same run. The universe is a bundled list (`GET /api/universes`) or the user's own tickers, checked against SEC's ticker list. The screener's draft spec and its questions are written to the trace (a `questions` event) and the run waits until the page sends the answers (an empty answer accepts the proposal); Cancel works while it waits. Its picks are researched by `WEB_DISCOVER_CONDITION` (B) unless Advanced options pick another. The shortlist shows each pick's answer with that claim's citations and flags, its report's other flags and an unfinished research run as warnings, and why the search ended (the run's notes, such as the research limit).

**Answer choices** (5 Nov 2026): each vague term also carries 2-3 `options`, concrete readings the screen can apply (filters, price checks, rankings with thresholds), one marked recommended. The recommended one is always the term's `definition`, the reading the spec applies; if the model marks another or leaves the definition out, the schema fixes that rather than refusing the term. The page shows them as choices with the recommended one picked, plus Other with a text box; the terminal numbers them (Enter accepts the recommended one, a number picks one, text is your own definition). Picking the recommended one, or leaving Other empty, accepts the proposal as before; another option or text sets the term and goes back to the model. A term without options keeps the plain text box. Sector-relative readings ("below the sector median") aren't offered: the screen computes no sector statistics.

**Bigger lists** (5 Nov 2026). `sp500` is the whole S&P 500 from the same Wikipedia table (503 tickers, 500 companies, all 11 GICS sectors, as of 2026-11-05, tickers in SEC's style such as BRK-B). Like `sp500_tech` it holds today's members only, so it is survivorship-biased and the page says so; it is the default Find list and the one Guide me uses. `sec_all` is every SEC filer with a ticker, built from SEC's ticker list on the day (CLI `--universe sec_all`; the page shows it disabled, with the reason, when SEC access isn't configured). Measured on a cold cache from this machine: SEC's list held 8,004 companies (3,453 Nasdaq, 2,592 NYSE, 2,040 OTC, 22 Cboe, 9 TXSE, 138 with no exchange); a fundamentals screen (operating margin above 25%, revenue growth above 0) took 11 s and 9 frames requests (2.5 MB), 3 s warm; adding a SIC sector filter took 6-8 minutes and about 1,200 submissions requests (150-170 MB), one per company passing the other filters, cached for a day. Price checks still run only on the walked shortlist. That is reasonable next to a research run, so it is offered, with these caveats in its note and spec: about half the companies come back unknown (funds, foreign filers, shells, banks for margins); the screener's prompt gives the list's size and source instead of 8,000 names (`Universe.show_members`); and a margin's inputs can come from different revenue tags or fiscal years, so the screen aligns or flags them (rule 8) and the acceptance test rechecks each pick on the latest 10-K. A size filter such as revenue keeps out most shells.

## 5. Finance and data cautions

**SEC fundamentals**
- Select facts by concept + period (start/end) + form + filed date. **Never** "take the last value in the array", and never use the `fy` field as the period (it is the filing's fiscal year).
- Revenue appears under several tags (`RevenueFromContractWithCustomerExcludingAssessedTax`, `Revenues`, `SalesRevenueNet`). Check all of them by recency. If values conflict for the same accession and period, abstain.
- ASC 606 contract revenue leaves out lease income (REITs) and interest (banks). So in companyfacts (`sec_facts.select`, behind Check, Compare and the acceptance test), as in frames (§4 rule 8), a larger `Revenues`, `SalesRevenueNet` or `RevenuesNetOfInterestExpense` in the same filing and period replaces it. The fact keeps its real tag, and a restatement only compares values under that tag, so a tag switch is not a restatement. A larger total only in an older filing is not used, and a warning says so. The tax-inclusive contract tag never replaces the tax-exclusive one (Brown-Forman's sales include excise tax). UDR's latest 10-K reports $11.4M of contract revenue and $1,712M in total; before this, its operating margin showed as 4,870%.
- A margin above 100% (`SCREEN_MAX_MARGIN`) on the latest 10-K is unknown in Discover's acceptance test too, and the line still cites the record. With totals read, such a margin means income beyond revenue (BitMine's crypto gains) or revenue under a tag neither path reads, and passing "operating margin > 25%" on it would mean nothing. The screen and the acceptance test judge a filter the same way.
- Today's companyfacts holds later restated values. Filtering by cutoff does **not** recreate what investors saw then.
- Banks and insurers usually have no `OperatingIncomeLoss`. Treat that as "unsupported" rather than failing silently.
- Many foreign filers (20-F) use IFRS (`ifrs-full`, e.g. TSMC), not `us-gaap`. `get_financials` reads them from the same companyfacts (decided 7 Nov 2026): each metric's `ifrs-full` tag comes after its US GAAP tags, borrowed from edgartools' fallback lists ([§10](#adopt-or-build-tool-by-tool-survey-of-2-nov-2026)). Net income and equity are the owners' lines (`ProfitLossAttributableToOwnersOfParent`, `EquityAttributableToOwnersOfParent`), as US GAAP's are the parent's. A filing that tags only `ProfitLoss` (which includes non-controlling interests) has `ProfitLossAttributableToNoncontrollingInterests` from the same filing and period subtracted; without it, that year's net income is withheld with a warning. The figures convert to USD like any other currency: TSMC's TWD needs FRED H.10, and without a key the 20-F's US$ convenience figures are shown and labelled, and a line without them is unsupported with the reason. IFRS 15 contract revenue (`RevenueFromContractsWithCustomers`) comes last and counts as contract revenue, like ASC 606's: a larger total in the same filing and period replaces it. TSMC's FY2025 20-F tags its NET REVENUE line only with it (`Revenue` only on its major-customer facts); HSBC tags neither, only `RevenueAndOperatingIncome`, which isn't read. Not read: long-term debt, because IFRS has no total and debt tags are never summed (TSMC's `LongtermBorrowings` is NT$31.8 billion of bank loans beside NT$926.6 billion of bonds), so EV is unsupported. SEC frames (`screen`, `get_peers`) read US GAAP tags only, since an IFRS filer's USD frame holds just its convenience translations.
- companyfacts can miss a filing's statements: on 7 Nov 2026 TSMC's FY2025 20-F (filed 16 April 2026) is there only as its cover share count, while HSBC's FY2025 20-F, also IFRS, is there in full. When the newest 10-K, 20-F or 40-F has only its cover in companyfacts, `get_financials` reads that filing's own inline XBRL (whole-company facts, as `verify_against_filing` reads them) and adds them as that filing's rows (decided 7 Nov 2026, `data/filing_facts.py`). So the usual rules apply: its comparative column becomes the latest value for the year before, and a difference from the older filing shows as a restatement. Each such value has the filing as its source and a note saying so, and a warning names the filing. If the filing can't be read, its figures are missing and the warning says why. For TSMC this turns a P/E of 55.1x on FY2024 profit into 35.7x on FY2025's.
- A US GAAP foreign filer may report in another currency: BABA tags three years in CNY per 20-F and only the latest in USD, a convenience translation of every line at one year-end rate. `get_financials` takes the currency most of a concept's annual rows are in, counted in the newest annual filing public at the cutoff (ties keep USD; so a later filing can't change a past query, and a change of currency keeps the newest year), and converts it to USD (decided 7 Nov 2026, [FX row in §10](#data-providers-by-kind-options-and-order)): a year's income and cash flow at that year's average daily rate, a balance at the last rate on or before its date, as ASC 830 and IAS 21 translate. Each record keeps the filed value and currency, the rate, its dates and source; `verify_against_filing` checks the filed value, and `calculate` notes a converted input (a growth rate then includes exchange-rate moves: BABA's fiscal 2026 revenue grew 2.7% in CNY and 4.4% in USD at Frankfurter's yearly averages of 7.2169 and 7.1007 CNY per dollar). With no rate, the filing's own USD figures are shown and labelled, and a figure with none stays unsupported.
- Fiscal years differ (AAPL ends in September, MSFT in June, NVDA in January), and some have 53 weeks. Label comparisons by period end. Consider TTM for cross-company comparison.
- Cash-flow statements are year-to-date. Q4 = annual − 9M only if definitions match. Never subtract balance-sheet values; never sum EPS.
- FCF = operating cash flow − capex is non-GAAP; watch the capex sign. Don't sum overlapping debt tags; say whether leases are included.
- A margin change is in **percentage points** (10% → 12% is +2 pp, not +20%).
- Zero or negative denominator → unavailable. Keep GAAP and non-GAAP labelled. A management statement proves the claim was made, not that it is true.
- A ticker is not a security, and a CIK is the filer. Map share classes (GOOG/GOOGL) so an issuer isn't counted twice.
- SEC fair access: a User-Agent with a real contact email, and under 10 requests/second.

**Prices and valuation**
- Choose the price adjustment (splits, dividends) explicitly and never double-adjust. Adjusted historical prices are not prices you could have traded at.
- Per-share numbers must use the same split basis as the price. Shares outstanding: `dei:EntityCommonStockSharesOutstanding` (cover-page date); `calculate` market_cap takes only `shares_outstanding`, never a weighted-average count.
- A 20-F or 40-F filer's US quote is often a depositary share (BABA's ADS is 8 ordinary shares), so ADS price × ordinary shares overstates the market cap. `get_financials` gives such a share count an `ordinary_shares_per_ads` fact from the **same filing's cover**: the `dei:Security12bTitle` of each listed class ("American Depositary Shares, each representing eight Ordinary Shares"; number words, digits and fractions such as "one-half of one"), or the Section 12(b) table when the tag is missing. A cover with no depositary class that never mentions American depositary shares, footnotes included, is a direct listing (ratio 1: Check Point, ASML), whatever the rest of the filing says about other companies' ADSs (an investments note on "Alibaba ADSs, each representing 8 ordinary shares"; decided 8 Nov 2026). A cover that lists the shares with no ratio while it names ADSs (TSMC tags only "Common Shares" and footnotes that they trade as ADSs) takes the ratio from the filing's own text, if every sentence there that ties a ratio to the ADS gives the same value (decided 7 Nov 2026, `FILING_RATIO_LOOKBACK_CHARS`). TSMC's FY2025 20-F says it once, in an Item 6 footnote: "each ADS represents five (5) common shares". Its Item 9 and Item 12D give no ratio, so reading those sections with `read_filing_section` would not help. Its FY2023 and FY2024 20-Fs state none, only counts (5,313,816,033 common shares represented by 1,062,763,201 ADSs, 5.00000003 each), and stay unsupported: a ratio is never inferred from counts. Two depositary classes, a title without a ratio, or a text that states none or several stay unsupported with the reason. `calculate` market_cap then takes `ads_ratio` = close per ADS ÷ ratio × ordinary shares, refuses a ratio from another filing, and warns when that filing is more than a year older than the price (`SHARE_FILING_MAX_AGE_DAYS`). Without the ratio it stays unsupported, and so do the P/E, P/S, P/B, FCF yield and EV built on it. BABA's 2026 20-F tags its cover count as "18,580,374,27" and prints the last 8 just after the tag, so companyfacts holds 1,858,037,427; a cover count cut off like that uses the printed number, with a note, and `verify_against_filing` checks it against the tag.
- Historical market cap = **as-traded (raw) close** × cover-page shares. yfinance's Close is already split-adjusted, so use it for current-price valuation only. Tiingo provides both raw and adjusted prices.
- 20 trading sessions ≠ 20 calendar days. Use an exchange calendar (holidays, DST).
- Survivorship: SEC ticker lists hold today's companies only. Never drop delisted losers or forward-fill their prices. Thirty current large caps make a case study, not a market result.

**Forecasts and backtests**
- An **LLM already knows what happened after a historical cutoff**. Date-filtering documents does not remove that knowledge, so LLM-based historical backtests are contaminated. Evaluate LLM judgement only **prospectively** (log now, score later), or on dates after the model's training cutoff.
- Overlapping 20-day labels are not independent. Split by date, purge immature labels, and keep an untouched test period.
- Every extra trial inflates the best result. Keep a trial log (see the PBO and Deflated Sharpe papers).
- Beating SPY is not the same as profit, and neither is the same as alpha. Brier score is not pure calibration. Compare models on the same cases.
- Macro data: use ALFRED vintages, not today's revised series.

**Other**
- A valid JSON schema, or two models agreeing, is not evidence a claim is supported.
- A timed-out API call may still be billed.

## 6. Outlook specification

**Decided 8 Nov 2026: the outlook forecasts what can be forecast, each with its track record.** It leads with how much the stock may move (risk forecast), how often companies like it kept growing (business forecast) and what today's price already assumes; the direction forecast comes last, with its measured skill. Quant analysis (factor exposures, a strategy lab, shortlist risk) sits beside it. Every number is a host-made record that narrative never edits (§1). Each is tested: on history when a statistical model makes it, live (saved before the outcome) when it doesn't. Build order: PROJECT_GUIDE Phase 6. The first spec (one probability of beating SPY from a logistic regression on price features) is now just the direction forecast.

**Why direction doesn't lead.** Scratch probes on 4-8 Nov 2026 used throwaway scripts (not in the repo), Yahoo adjusted closes of today's `sp500_tech` members against SPY over 2010-2026, so they are survivorship-biased:

| Horizon (sessions) | Independent windows | Base rate (beat SPY) | 12-1 momentum, AUC | EWMA 80% range caught |
|---|---|---|---|---|
| 1 | 4,232 | 50.2% | 0.510 ± 0.004 | 84.5% |
| 5 | 846 | 51.1% | 0.511 ± 0.008 | 81.8% |
| 20 | 211 | 51.9% | 0.512 ± 0.016 | 78.4% |
| 63 | 67 | 52.5% | 0.499 ± 0.020 | 77.0% |
| 252 | 16 | 54.0% | 0.475 ± 0.044 | 75.5% |

- Outcomes move together: on one date the share of stocks beating SPY ran from 20% to 78%, so 20 sessions give about 211 independent dates, not 20,000 rows. The base rate climbs with the horizon because survivors compound.
- A three-way rating by thirds of the universe, from momentum, put 35.4% ± 1.4% of its calls in the right third (33.3% by chance); the top-minus-bottom gap was +0.45% ± 0.68% per 20 sessions. Momentum's rank correlation with the next 20 sessions' excess return was 0.012.
- Risk is predictable: EWMA volatility and the next 20 sessions' realised volatility had a rank correlation of 0.59. The chance of trailing SPY by more than 10% rose from 3.1% for the calmest fifth to 14.8% for the most volatile fifth. A constant range caught 62-93% depending on the year, EWMA 76-81%. In the 19 windows where SPY fell more than 5%, a beta-scaled 80% range caught 76%.
- So are fundamentals. On the 82 companies in the SEC cache (first-reported 10-K values), base rates learned on years up to 2016 predicted P(next-year revenue growth above 10%) on 2017 on with Brier skill +11.5% against one rate; the buckets said 59, 70 and 76% and came true 60, 71 and 77% of the time. Low-growth buckets were too pessimistic (said 24-26%, came true 32-37%), a shift in era the test shows. The lowest-margin fifth raised its margin the next year 69% of the time (skill +2.3%).
- The research agrees ([§10](#outlook-evidence-papers)): even 920 signals explain about 0.4% of a month's stock returns (Gu, Kelly & Xiu 2020); growth barely persists (Chan, Karceski & Lakonishok 2003) and profitability reverts about 38% a year (Fama & French 2000).

**Timing, records and tests** (every part)
- **Cutoff and windows:** a day's close counts from `PRICE_CLOSE_AVAILABLE_HOUR` (18:00 New York). Anchor = the next session's close; end = 5 or 20 sessions later on the XNYS calendar (`exchange_calendars`). A record saved after its anchor is "missed", never moved.
- **Returns:** dividend-adjusted closes, the stock and SPY from the same provider (§10 provider rule 6). Ties count as 0; an unmeasurable window (delisted, missing close) is unresolved, never 0.
- **Records:** values, the IDs of their inputs, model and data versions, issue time. Immutable. Outcomes go in a separate file. The live log is append-only and each line carries the hash of the one before.
- **Splits:** by date across all companies; training rows whose window crosses the test start are dropped (purge); calibration uses an earlier block than the test; one final period stays untouched until the model is frozen. Every configuration tried goes in a trial log and is counted in the results (PBO, Deflated Sharpe in §10).
- **Uncertainty:** bootstrap by date block or year, never by row.
- **Status:** available, unavailable (with the reason), missed, pending or resolved, kept apart from report support (§1).

**WRDS rules** (from [HKU's guide](https://libguides.lib.hku.hk/c.php?g=766106&p=5501197) and WRDS's [terms](https://wrds-www.wharton.upenn.edu/users/tou/), [download policy](https://wrds-www.wharton.upenn.edu/pages/about/data-download-and-analysis-policy/), [AI policy](https://wrds-www.wharton.upenn.edu/pages/about/ai-policy-on-chatgpt-and-other-generative-ai-tools/) and [system policies](https://wrds-www.wharton.upenn.edu/pages/about/system-policies/), read 8 Nov 2026)
- **Account:** HKU faculty, research assistants and students can register a personal account on the WRDS site. Never share credentials or put them in the repo. Masters and undergraduate accounts are shut during the long break between semesters. Access ends with the HKU affiliation, and downloaded data must then be deleted.
- **No LLM ever sees WRDS data.** WRDS bans loading its data into LLMs and generative AI tools. Its narrow exceptions (some vendors' data in protected enterprise tools) don't cover CRSP or I/B/E/S. So no agent, critic, prompt or AI coding tool (Claude Code, Codex) opens WRDS data or files; results reach the report through people.
- **Where to work:** run on WRDS Cloud (Python, batch jobs through its grid) and bring back result tables only. HKU forbids bulk download of library-subscribed resources by API, while WRDS allows remote database connections and automation on WRDS Cloud, so ask the library before pulling large extracts to a laptop. The `wrds` package (3.5.0) pins pandas below 2.3, which clashes with our pandas 3.1, so use it on WRDS Cloud or in a separate environment.
- **Sharing:** academic use only. No raw or per-company WRDS data in git (`/data/` is ignored) or on any shared server. Publish aggregates and cite: "Wharton Research Data Services (WRDS) was used in preparing …".
- **Coverage:** HKU says it doesn't subscribe to every WRDS dataset. After logging in, check the dataset list (CRSP's stock files, not only the CRSP/Compustat link).

**Horizons:** 5 and 20 sessions for the risk and direction forecasts. One session only for results-day moves. No hourly forecasts: Yahoo keeps 730 days of hourly bars and 8 days of minute bars, and any edge is below trading costs. No yearly price forecast: 16 independent windows, where survivorship bias is worst. The outside view is yearly because fundamentals are.

**Showing it** (§9)
- **Simple view:** counts, not percentages ("52 of 100 comparable windows"), with icons for a chance ("15 of 100 dots"). Fixed words for chances, adapted from the IPCC scale: very unlikely below 10%, unlikely 10-33%, about as likely as not 33-66%, likely 66-90%, very likely above 90%. So words never sound surer than the number.
- **Details view:** error bars, the reliability plot with counts, coverage by year, the exact target and window, and a model card (sample, period, survivorship note, data source, version, number of trials).
- **Always:** "statistical, not advice", backtests labelled "hypothetical", and other people's views (analyst consensus, the option-implied range) labelled with their source and date.

**LLM-based predictions** are tested only live. An LLM already knows what happened after a historical date, and telling it to ignore that doesn't work (§5, §10 papers). Optional later: log the agent's stated view next to the statistical records and the analyst consensus, scored the same way, and call it a pilot until many windows have resolved.

**Not built, on purpose:** a "buy" signal, or a rating or screen backtest on survivor-only data (coin-flip skill, biased history, reads as advice); trade execution and portfolio optimisation (out of scope); searching many rules or factors for the best backtest (every extra trial inflates the best result, §5); hourly or yearly price forecasts (above); probabilities stated by an LLM (overconfident and untestable on history); ready-made forecasting models such as Chronos, TimesFM and Kronos (negative R² on daily returns as-is, and their training data covers our test years); 8-K event averages presented as forecasts (every event differs and the spread swamps the average).

## 7. Evaluation protocol

**Research question:** does an analyst team with a critic and revision loop give more correct, better-supported research than simpler set-ups, at acceptable cost?

| Condition | What it is | What it isolates |
|---|---|---|
| **A** | Deterministic pipeline + report template (the existing code) | What plain software already solves |
| **B** | Single agent, all tools, one self-review pass | Value of tools and the loop |
| **C** | Analyst team, no critic | Value of role specialization |
| **D** | Analyst team + critic + revision | The full system |

- **Isolated review test:** start from the **same saved draft and evidence**, then compare no revision, self-review and critic-guided revision. Use frozen evidence so that retrieval differences don't confound the result. CLI: `--review TRACE` runs D's critic and revisions on a saved run's final draft and records (`agents/isolated_review.py`); `--inject wrong_period` first swaps one key figure for an earlier fiscal year's fact from the same records while its words still name the later year, written to the trace as its own claim version by "injected". The draft and records are frozen, but the team's tools still run (mostly from the SEC disk cache). A price series fetched again can differ by float noise (Yahoo's adjusted closes), so its ID covers its rows and each version stays frozen under its own ID; `--recheck` recomputes a calculation from every version frozen under its inputs' IDs, for older traces that hold two under one (PROJECT_GUIDE Phase 3).
- **Cases:** a development set for tuning plus a separate held-out set that is never used for tuning. Mix of check, compare and discover questions, plus robustness cases: clean (the critic should change nothing), wrong period or unit, restatement, missing data, unknown ticker, impossible filter, API failure, injected instruction in filing text, look-ahead (a past cutoff and a question that invites what the model remembers; `must_not` names the later events). Label injected defects separately. Cases built on the same gold list each other in `related` and stay in one split, so the held-out set doesn't leak (a test enforces it).
- **Fair comparison:** A only covers what the old pipeline supports (five companies, annual figures), so compare A with the others only on those cases. B, C and D get the same cases, data and scoring. B's self-review and D's critic look for the same issue types (§3), not just checker flags. Decided in Phase 4: the self-review pass (`runner.py`, shared by B, C and D) always runs once, even on a draft the checker passes, and shows the lead the same issue list, claim view and evidence view as the critic (`agents/objections.py`); a second pass (`AGENT_SELF_REVIEW_PASSES` > 1) runs only while checker flags remain. So C keeps B's self-review and B vs C still isolates specialization, and D is C plus the critic. Compute isn't matched exactly, so report quality next to steps, tokens, cost and time rather than claiming a compute-matched baseline.
- **Gold labels:** written from SEC data by one person, without seeing system output. A second person checks a sample (at least 10 cases), and the report says how many were checked and how many were changed. Gold answers never appear in tool outputs.
- **Metrics:**
  - Numeric accuracy (value, period, unit) and citation validity (automatic)
  - Claim support, judged by humans on a sample (an LLM judge may triage only)
  - Coverage of required facts, so that omission can't win
  - Critic effect: wrong→right fixes, right→wrong damage, valid-objection precision
  - Risk coverage, justified abstention, and discover-mode correctness (filters satisfied, replacements correct)
  - Steps, tokens, cost, median and p95 latency, failure rate
- **Stats:** paired comparisons per case, bootstrap intervals, repeated runs on a subset to measure randomness. Label small samples "exploratory". Negative results are fine.
- **Freeze** the model ID and prompts before the held-out run, and upgrade nothing mid-ablation. Within one batch `eval/run_eval.py` enforces this: its `manifest.json` records the model, prompt and case-file hashes, the relevant `config.py` values and the git commit, and a resume with any of them changed is refused.
- **Component benchmarks (optional):** FinQA or TAT-QA for numeric reasoning, AgentDojo-style injection cases.

## 8. Security and prompt injection

- The host owns trusted context (run ID, cutoff, allowed evidence IDs). These never come from model arguments.
- Fixed tool registry. No eval, dynamic import, model-written SQL/Python/shell, broker tools or arbitrary URLs.
- Validate tool arguments (types, ranges, ticker exists, date ≤ cutoff). Cap payload sizes on **input** to tools; never truncate output silently.
- Sanitize retrieved HTML. API keys stay server-side; redact secrets in logs. The server listens on localhost only.
- Test case: an instruction hidden in filing text must not change the cutoff, widen tools or leak keys.

Guide me** (first called Help me start), for a user with no company or criteria in mind: four multiple-choice questions (what matters most, time horizon, comfort with price swings, sector), each with a recommended answer and "Not sure", become a Find question over the biggest bundled list plus a preferences note, both editable. ### Data providers by kind (options and order)

Every kind of data has a few options, so nothing depends on one vendor. These rules apply to every kind:
1. **Tiers:**
   - **0** = free, no key
   - **1** = free with a key
   - **2** = paid

   Build tier 0 first, then tier 1. Write a paid adapter only when nothing free does the job, and leave it switched off until its key is in `.env`.
2. **Order:** each kind's provider list lives in `config.py`, in priority order. An env variable can override it, for example `PRICE_PROVIDERS=tiingo,yfinance`.
3. **Missing key means skipped, not an error.** The status page shows that provider as "not configured" and names the variable to set.
4. **Zero keys must work out of the box.** The only required settings are `SEC_USER_AGENT` (an email) and an LLM key. Adding a key upgrades that kind; removing one falls back.
5. **Fallback is allowed but never silent.** Every result carries `source`, and the trace records any provider that was skipped or failed.
6. **One series, one provider.** Don't mix providers inside one calculation, such as one price history. The evaluation pins the provider list so results are reproducible.
7. **No provider available** means the tool returns "unavailable: needs X", and the agent says so in the report.

**Status** (survey of 4 Nov 2026): **in use**; **next** = the shortlist for November 2026, ranked (1) to (7); **later**; **no**, with the reason. **Point-in-time** = usable at a past cutoff without later information. Terms to respect: Finnhub's free licence is personal use; Tiingo and EODHD data is for internal use; prefer the primary source over the many new wrappers on public-apis (one less dependency and citation hop). The next seven add about 11–13 days of work with AI help. A new tool changes conditions B–D, so land it before the held-out run is frozen, or keep it out of the evaluated tool set (web app only).

**Other HKU databases** ([database list](https://libguides.lib.hku.hk/az.php?s=154482), read 8 Nov 2026). The §6 WRDS rules apply to everything reached through WRDS: people work on it, no LLM or AI coding tool opens the data, and only aggregates reach the report.
- **Worth using, offline:**
  - **Audit Analytics** (restatements, going-concern opinions, auditor changes, control weaknesses): a person uses it to find restatement and going-concern examples, then writes each eval case from the SEC filings themselves, so no Audit Analytics data sits in a case. It also gives report-only base rates, such as how often a control weakness came before a restatement.
  - **I/B/E/S Guidance**: how often companies met the guidance they gave, as a report-only base rate next to the filings analyst's attributed management claims.
  - **Eventus** (event studies on CRSP): abnormal returns after 8-K events, insider purchases and earnings, done the standard way for the report. With free data alone, those event averages stay unbuilt (§6).
- **For the report:** JSTOR, EconLit, Web of Science, SSRN (Financial Economics Network) and ProQuest give the original papers behind numbers in [Outlook evidence](#outlook-evidence-papers) that came from summaries (Lazy Prices, McLean & Pontiff, Chan, Karceski & Lakonishok, Barber et al.). People read and cite them; licensed full texts aren't fed to AI tools unless the licence allows.
- **Not needed:**
  - TAQ: tick data, and no horizon here is intraday.
  - Fama-French through WRDS: the same as the free Ken French site.
  - Bank Regulatory: FFIEC's free call reports have the same data if banks are ever supported.
  - DealScan, Mergent FISD, BoardEx, ISS and SDC: loans, bonds, boards and deals.
  - Compustat Global, PACAP, and the Hong Kong and China databases: outside the US-listed scope.
  - Factiva and the FT and Economist archives: news text, whose licences ban bulk text mining, and an LLM would already know what came after.
  - Finaeon, EIU, EMIS, Orbis, IRI and the rest: off-topic.

### Outlook evidence (papers)
Read on 4-8 Nov 2026 for the Phase 6 decision (§6). Summaries for some came from secondary pages; check the paper before quoting a number in the report.

| Paper | Finding | How we use it |
|---|---|---|
| [Gu, Kelly & Xiu 2020](https://dachxiu.chicagobooth.edu/download/ML.pdf) (RFS, Table 1) | Monthly stock-level R² 0.33-0.40% with neural nets on 920 signals, 0.16% for size, value and momentum alone, −3.46% for unregularised OLS; 0.52-0.70% for the largest 1,000 stocks | Why direction doesn't lead and why a big model wouldn't help |
| [Bessembinder 2018](https://econpapers.repec.org/RePEc:eee:jfinec:v:129:y:2018:i:3:p:440-457) (JFE) | 47.8% of monthly stock returns beat one-month T-bills; a few big winners drive the market | Base rates below 50%; survivors inflate ours |
| [Grinold's fundamental law](https://www.cfainstitute.org/insights/professional-learning/refresher-readings/2025/analysis-active-portfolio-management) (CFA reading) | Skill pays only across many independent bets; typical forecast ICs are 0.02-0.10 | Why a weak signal is no verdict on one stock |
| [The Base Rate Book](https://hedgefundalpha.com/education/michael-mauboussin-the-base-rate-book/) (Mauboussin, Callahan & Majd, Credit Suisse 2016) | Sales growth barely persists; base rates for growth, margins and returns by size | The business forecast's method |
| [Chan, Karceski & Lakonishok 2003](https://www.nber.org/papers/W8282) (JF) | No persistence in long-term growth beyond chance; analysts' growth forecasts too optimistic | The critic's base-rate check |
| [Fama & French 2000](https://econpapers.repec.org/RePEc:ucp:jnlbus:v:73:y:2000:i:2:p:161-75) (JB) | Profitability reverts to the mean about 38% a year, faster when far from it | Margin buckets in the outside view |
| [Expectations Investing](https://expectationsinvesting.com/) (Mauboussin & Rappaport, revised 2021) | Read the expectations in the price with a reverse DCF instead of forecasting the price | The implied-growth part |
| [Lazy Prices](https://www.nber.org/papers/w25084) (Cohen, Malloy & Nguyen 2020, JF) | Firms that change their 10-K text, especially risk factors, did worse: up to 188 bp a month long-short, 1995-2014 | Filing-change alerts (second stage) |
| [McLean & Pontiff 2016](https://ivey.uwo.ca/media/3775549/pontiff.pdf) (JF) | 97 predictors: returns 26% lower out of sample, 58% lower after publication | Expect published effects to shrink; the strategy lab shows it |
| [Barber, Lehavy, McNichols & Trueman 2001](https://econpapers.repec.org/RePEc:bla:jfinan:v:56:y:2001:i:2:p:531-563) (JF) | Top consensus ratings beat the market by over 4% a year before costs, 1986-96, but not after | Why analysts' ratings are context, not our signal |
| [Martineau 2022](https://nowpublishers.com/article/Details/CFR-0122) (CFR), [disputed in 2025](https://anderson-review.ucla.edu/is-post-earnings-announcement-drift-a-thing-again/) | Drift after earnings has been gone for large stocks since about 2006 | Results-day moves are risk, not a signal |
| [Lopez-Lira, Tang & Zhu 2025](https://arxiv.org/abs/2504.14765) | LLMs recall exact pre-cutoff market values; telling them to ignore the future doesn't work | LLM predictions only live (§5) |
| [Glasserman & Lin 2023](https://arxiv.org/abs/2309.17322) | GPT sentiment backtests mix look-ahead and a "distraction" effect; anonymising names changes results | Same |
| [Lopez-Lira & Tang 2023](https://arxiv.org/abs/2304.07619) | ChatGPT headline scores predicted next-day returns; later versions add post-cutoff headlines | Example of a study that had to address contamination |
| [Profit Mirage 2025](https://arxiv.org/abs/2510.07920) | Published LLM trading agents stop beating a random baseline after their training cutoff (FinLake-Bench) | Same |
| [FINSABER 2025](https://arxiv.org/abs/2505.07078) | Reported LLM investing advantages fade over 20 years and 100+ stocks | Same |
| [He, Lv, Manela & Wu 2025](https://arxiv.org/abs/2502.21206) (ChronoBERT/ChronoGPT) | Models trained only on text available at each date: the clean way to backtest an LLM | Why we don't backtest ours |
| [LiveTradeBench](https://arxiv.org/abs/2511.03628), [Agent Market Arena](https://arxiv.org/abs/2510.11695), [ForecastBench](https://www.forecastbench.org) | Live or prospective evaluation of LLM forecasts and agents, scored by Brier or returns | The live log's design |
| [Xiong et al. 2024](https://arxiv.org/abs/2306.13063) (ICLR) | LLMs' stated confidence is highly overconfident | No LLM-stated probabilities |
| [Kim, Muhn & Nikolaev 2024](https://arxiv.org/abs/2407.17866) | GPT-4 predicted earnings direction from anonymised statements about as well as a trained model; memorisation doubts remain | A possible live test of the agent against the outside view |
| [Rahimikia, Ni & Wang 2025](https://arxiv.org/abs/2511.18578); [Kronos](https://arxiv.org/abs/2508.02739) | Off-the-shelf time-series foundation models had negative R² on daily excess returns; Kronos claims gains in its own tests | Ready-made forecasting models skipped |
| [Natural frequencies](https://pmc.ncbi.nlm.nih.gov/articles/PMC4504147) (Gigerenzer & Hoffrage), [IPCC likelihood scale](https://www.ipcc.ch/site/assets/uploads/2017/08/AR5_Uncertainty_Guidance_Note.pdf), [model cards](https://arxiv.org/abs/1810.03993), [SEC marketing rule on hypothetical performance](https://www.troutman.com/insights/the-secs-new-marketing-rule-practically-speaking-hypothetical-performance/) | Counts read easier than percentages (evidence mixed); fixed words for chances; a model's sample, limits and version on one card; backtests shown to ordinary investors are restricted | The Simple and Details views |
